# 01. Principes

Les règles couvrent les cas prévus. Les principes servent pour tous les autres.

## La production d'abord

Ce qui tourne chez les utilisateurs passe avant ce qui tourne sur nos postes. Une fonctionnalité brillante qui fragilise la production n'est pas un progrès ; c'est une dette contractée sans l'accord de ceux qui la paieront.

## Petit, souvent, réversible

Un gros changement concentre le risque et dilue la responsabilité. On découpe jusqu'à ce que chaque morceau puisse partir seul et revenir en arrière sans drame.

## Écrire pour décider

Une discussion orale s'évapore. Un paragraphe reste, se relit, se conteste. Dès qu'une décision engage plus d'une personne ou plus d'une semaine, elle s'écrit.

## Le comportement réel fait foi

Ni la spécification ni le souvenir de quelqu'un ne disent ce que fait le système. Seuls le code qui tourne, ses journaux et ses tests le disent. Avant d'affirmer, on vérifie.

## Pas de coupable, des causes

Quand quelque chose casse, la question n'est jamais « qui ? ». Elle est « qu'est-ce qui a rendu l'erreur possible, et qu'est-ce qui l'aurait arrêtée ? ». Une équipe qui a peur cache ses incidents. Une équipe qui les raconte les corrige.

## Le produit et la technique forment une seule équipe

Le développeur qui ignore pourquoi il construit prend de mauvaises décisions avec beaucoup d'application. Le responsable produit qui ignore ce que coûte une demande promet n'importe quoi. Chacun doit comprendre assez le métier de l'autre pour lui poser les bonnes questions.

## Garder la main dans le code

Diriger une équipe technique sans lire le code, c'est piloter aux instruments sans savoir les lire. Je relis, je teste, je descends dans les journaux quand un incident l'exige. Pas pour contrôler. Pour rester crédible quand j'arbitre.
